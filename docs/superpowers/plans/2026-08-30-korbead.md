# korbead Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a JSON/HTTP service in korben that serves this repository's beads data, to find out empirically what actually stands between korben and production use.

**Architecture:** A multi-module korben package built outside the korben repository against an installed `korben` binary. The read side loads a `bd list --all --json` snapshot; the write side is a service-owned notes overlay. Correctness is established by diffing computed endpoints against `bd` itself. A load-and-profile run then tests three hypotheses that decide korben's runtime roadmap.

**Tech Stack:** korben 0.10.0 (`std.http`, `std.json`, `std.fs`, `std.string`, `std.log`, `std.time`, `std.process`), `bd` for oracle data, `oha` for load generation, `samply` for profiling, `python3` for oracle diffing.

**Spec:** `docs/superpowers/specs/2026-08-30-korbead-dogfood-design.md`

**Beads:** epic `korben-8fl`, children `korben-8fl.1` … `korben-8fl.7`

---

## Global Constraints

- **No changes to korben.** Not the runtime, not the stdlib, not the compiler. Every wall hit is filed as a bead with `-l runtime-gap` and the text `DEFERRED by decision: not to be implemented during the korbead dogfood project.` Then work around it or document it — never fix it.
- **korbead lives outside the korben repository.** Suggested `~/repo/korbead`. It must not be a member of the korben cargo workspace.
- **Driven by an installed binary**, from `cargo install --path crates/korben-cli` run inside the korben repo.
- **JSON maps are Keyword-keyed.** `(get issue :id "")` works; `(get issue "id" "")` silently returns the default. Verified against the real binary. See bead `korben-3cb`.
- **`http.Request` maps are String-keyed.** `request.query` and `request.headers` are `Map String String`. This is the opposite convention from decoded JSON. Both appear in this codebase; do not mix them up.
- **`get` takes a default as its third argument:** `(get collection key default)`.
- **Collection-first argument order:** `(filter coll pred)`, `(map coll f)`, `(reduce coll init f)`.
- **Match guards come between pattern and result:** `pattern :when (predicate) result`.
- **No signal handling exists.** The service cannot drain or exit cleanly. Do not try to add it. Bead `korben-5k7`.
- **No `std.fs/rename` exists.** Overlay writes cannot be atomic. Do not try to add it. Bead `korben-0mo`.
- **The verification gate is `korben check && korben test`, never `korben test` alone.** Discovered during Task 3 and reproduced minimally: `korben test` does not typecheck the program at all. A function declared `-> Int` returning a `String` gives `success: 1/1 test passed` from `korben test` and a hard error from `korben check`. A green suite is not evidence the code compiles. Bead `korben-yjw` (P1). Every task that runs tests must run `korben check` too, and `korben build` where the task produces a runnable artifact.
- **Commit after every task.** korbead has its own git repository, initialised in Task 1.

;;; Loading and querying the beads snapshot.
;;;
;;; The snapshot comes from `bd list --all --json`, so every issue is a map
;;; keyed by Keyword — `(get issue :id "")`, never `(get issue "id" "")`.
(module issues
  (use std.json :as json)
  (use std.fs :as fs))

;;; Read a snapshot. A missing or malformed file is an error rather than an
;;; empty list, so a misconfigured deployment fails loudly at startup instead
;;; of serving nothing and looking healthy.
(pub fn load [path: String] -> Result (Vec (Map Keyword String)) String
  (match (fs.read-text path)
    (Err cause) (Err (format "cannot read {path}: {cause}"))
    (Ok text)
      (match (json.decode text)
        (Err cause) (Err (format "cannot parse {path}: {cause}"))
        (Ok data)
          (if (= (type-of data) "Vec")
            (Ok data)
            (Err (format "{path} is a {(type-of data)}, expected a JSON array"))))))

(pub fn id-of [issue] -> String (get issue :id ""))
(pub fn status-of [issue] -> String (get issue :status ""))
(pub fn type-of-issue [issue] -> String (get issue :issue_type ""))
(pub fn priority-of [issue] -> Int (get issue :priority 0))
(pub fn title-of [issue] -> String (get issue :title ""))

;;; The issue with a given id, if the snapshot has one.
(pub fn find [all id: String] -> Option (Map Keyword String)
  (match (filter all (fn [issue] (= (id-of issue) id)))
    [] (None)
    [first ...rest] (Some first)))
```

### Task 3: Queries — filtering, readiness, and stats

**Bead:** `korben-8fl.2` (completes it)

**Files:**
- Modify: `src/issues.kb`
- Modify: `tests/issues_test.kb`

**Interfaces:**
- Consumes: `issues.load`, `issues.id-of`, `issues.status-of` from Task 2.
- Produces:
  - `(issues.open-only [all] -> Vec (Map Keyword String))`
  - `(issues.by-status [all status: String] -> Vec ...)`
  - `(issues.by-type [all kind: String] -> Vec ...)`
  - `(issues.by-priority [all priority: Int] -> Vec ...)`
  - `(issues.matching [all needle: String] -> Vec ...)`
  - `(issues.ready [all] -> Vec ...)`
  - `(issues.stats [all] -> Map Keyword Int)`

**Readiness rule, verified against `bd`:** an issue is ready when its status is not `closed` and every dependency of type `blocks` names an issue that *is* closed. Dependencies of type `parent-child` and `discovered-from` do not block. In the `bd list` form each dependency is a map with `:depends_on_id` and `:type`. A `blocks` dependency naming an id absent from the snapshot is treated as blocking — an unknown blocker is not a satisfied one.

;; ------------------------------------------------------------------ filters

(pub fn open-only [all] -> Vec (Map Keyword String)
  (filter all (fn [issue] (not= (status-of issue) "closed"))))

(pub fn by-status [all status: String] -> Vec (Map Keyword String)
  (filter all (fn [issue] (= (status-of issue) status))))

(pub fn by-type [all kind: String] -> Vec (Map Keyword String)
  (filter all (fn [issue] (= (type-of-issue issue) kind))))

(pub fn by-priority [all priority: Int] -> Vec (Map Keyword String)
  (filter all (fn [issue] (= (priority-of issue) priority))))

;;; Issues whose title contains `needle`, ignoring case.
(pub fn matching [all needle: String] -> Vec (Map Keyword String)
  (let wanted (string.lower needle))
  (filter all (fn [issue] (contains? (string.lower (title-of issue)) wanted))))

;; ---------------------------------------------------------------- readiness

;; A dependency blocks when it is of type `blocks` and the issue it names is
;; not closed. An id the snapshot does not contain is treated as blocking: an
;; unknown blocker is not a satisfied one.
(fn dependency-satisfied? [all dependency] -> Bool
  (if (not= (get dependency :type "") "blocks")
    true
    (match (find all (get dependency :depends_on_id ""))
      (None) false
      (Some blocker) (= (status-of blocker) "closed"))))

;;; Open issues with no unsatisfied blocking dependency. Mirrors `bd ready`.
(pub fn ready [all] -> Vec (Map Keyword String)
  (filter (open-only all)
    (fn [issue]
      (all? (get issue :dependencies []) (fn [d] (dependency-satisfied? all d))))))

;; -------------------------------------------------------------------- stats

;;; Counts by status, mirroring `bd stats`.
(pub fn stats [all] -> Map Keyword Int
  {total (len all)
   open (len (open-only all))
   closed (len (by-status all "closed"))
   in_progress (len (by-status all "in_progress"))
   blocked (- (len (open-only all)) (len (ready all)))
   ready (len (ready all))})
```

Create `src/routes.kb`:

```korben
;;; Routing. Handlers are ordinary functions over ordinary records, so every
;;; one of them is testable without a socket.
;;;
;;; Two key conventions collide here and it matters: `request.query` is keyed
;;; by String, while issues decoded from JSON are keyed by Keyword.
(module routes
  (use issues :as issues)
  (use std.http :as http)
  (use std.json :as json)
  (use std.string :as string))

;;; The id in "/issues/korben-8fl". Empty when the path carries none.
(pub fn issue-id [path: String] -> String
  (match (string.split-once path "/issues/")
    (None) ""
    (Some parts) (get parts 1 "")))

;; Apply whichever filters the query string asked for. No parameter means the
;; open issues, which is the useful default for a work tracker.
(fn selected [all query: Map String String] -> Vec (Map Keyword String)
  (let by-state
    (match (get query "status" "")
      "" (issues.open-only all)
      wanted (issues.by-status all wanted)))
  (let by-kind
    (match (get query "type" "")
      "" by-state
      wanted (issues.by-type by-state wanted)))
  (let by-rank
    (match (get query "priority" "")
      "" by-kind
      wanted (match (string.parse-int wanted)
               (Err _) by-kind
               (Ok value) (issues.by-priority by-kind value))))
  (match (get query "q" "")
    "" by-rank
    needle (issues.matching by-rank needle)))

(pub fn handle [all request: http.Request] -> http.Response
  (match request
    {:method :get :path "/health"} (http.text 200 "ok")

    {:method :get :path "/issues"}
      (http.json 200 (json.encode (selected all request.query)))

    {:method :get :path "/ready"}
      (http.json 200 (json.encode (issues.ready all)))

    {:method :get :path "/stats"}
      (http.json 200 (json.encode (issues.stats all)))

    {:method :get :path p} :when (string.starts-with? p "/issues/")
      (match (issues.find all (issue-id p))
        (Some issue) (http.json 200 (json.encode issue))
        (None) (http.not-found))

    _ (http.not-found)))
```

```korben
;;; The notes overlay: the only state korbead owns.
;;;
;;; Beads' jsonl is a passive export and mutations belong to Dolt, so korbead
;;; never writes beads state. Notes are its own, keyed by issue id.
;;;
;;; The whole file is rewritten on every append. There is no `std.fs/rename`
;;; in korben today, so this write is NOT atomic: a crash between truncation
;;; and completion loses the overlay. See bead korben-0mo. This is recorded
;;; rather than worked around, on purpose.
(module notes
  (use std.json :as json)
  (use std.fs :as fs))

;;; Read the overlay. A missing file is an empty overlay — unlike the snapshot,
;;; the absence of notes is the ordinary starting state, not a misconfiguration.
(pub fn load [path: String] -> Map Keyword (Vec String)
  (match (fs.read-text path)
    (Err _) {}
    (Ok text) (match (json.decode text) (Err _) {} (Ok data) data)))

;;; The notes recorded against one issue, oldest first.
(pub fn for-issue [store id: String] -> Vec String
  (get store (keyword id) []))

;;; Record a note. Returns the new overlay; the old one is unchanged.
(pub fn append [store id: String text: String] -> Map Keyword (Vec String)
  (assoc store (keyword id) (conj (for-issue store id) text)))

;;; Persist the overlay. Not atomic — see the module comment.
(pub fn save [path: String store] -> Result Unit String
  (match (fs.write-text path (json.encode store))
    (Err cause) (Err (format "cannot write {path}: {cause}"))
    (Ok _) (Ok nil)))
```

```korben
;;; The id in "/issues/korben-8fl/notes". Empty when the path is not a notes path.
(pub fn notes-id [path: String] -> String
  (match (string.split-once path "/issues/")
    (None) ""
    (Some parts)
      (match (string.split-once (get parts 1 "") "/notes")
        (None) ""
        (Some inner) (get inner 0 ""))))

;;; Routing including the notes overlay.
;;;
;;; `store` is a `Cell` rather than a plain map because the handler must record
;;; notes across requests. A handler closure capturing a Cell is verified to
;;; satisfy `http.serve`'s `(-> [Request] Response)`, to mutate across
;;; requests, and to perform `!io`.
;;;
;;; `notes-path` is here because persistence has to happen INSIDE the handler:
;;; `http.serve` calls the handler directly and offers no interception point
;;; where a caller could persist afterwards.
(pub fn handle-with-notes [all
                           store: (Cell (Map Keyword (Vec String)))
                           notes-path: String
                           request: http.Request] -> http.Response !io
  (match request
    {:method :get :path p} :when (string.ends-with? p "/notes")
      (match (issues.find all (notes-id p))
        (None) (http.not-found)
        (Some _) (http.json 200 (json.encode (notes.for-issue (store.get) (notes-id p)))))

    {:method :post :path p} :when (string.ends-with? p "/notes")
      (match (issues.find all (notes-id p))
        (None) (http.not-found)
        (Some _)
          (do
            (store.update (fn [current] (notes.append current (notes-id p) request.body)))
            ;; Not atomic: there is no `std.fs/rename`. See bead korben-0mo.
            (match (notes.save notes-path (store.get))
              (Err cause) (http.json 500 (json.encode {:error cause}))
              (Ok _) (http.json 201 (json.encode (notes.for-issue (store.get) (notes-id p)))))))

    _ (handle all request)))
```

  (match (process.env name)
    (Some value) :when (not (empty? value)) value
    _ fallback))

(fn issues-path [] -> String (setting "KORBEAD_ISSUES" "data/issues.json"))

    (fn [path]
      (let response (routes.handle-with-notes all store (notes-path) (http.test-request :get path)))

(pub fn main [] -> Unit !io

    ;; A snapshot that will not load is a misconfiguration, and the process
    ;; says so and exits non-zero rather than serving an empty tracker.

        (log.error "cannot load the snapshot" {path (issues-path) cause message})
        (process.exit 2))

        (let store (Cell.new (notes.load (notes-path))))

              (log.info "listening" {address (address)})
              (log.warn "no signal handling: this process can only be killed" {bead "korben-5k7"})

                                 (fn [request] (routes.handle-with-notes all store (notes-path) request)))
                (Ok _) nil
                (Err error) (do (log.error "server stopped" {cause (http.describe error)}) (process.exit 1))))
          _ (self-check all store)))))

### Task 7: The oracle diff harness

**Bead:** `korben-8fl.5`

**Files:**
- Create: `bin/oracle.sh`

**Interfaces:**
- Consumes: a running korbead on `KORBEAD_ADDR`, and `bd` in the korben repo.
- Produces: exit 0 when korbead agrees with `bd`, non-zero with a diff when it does not.

**What this actually proves:** `/ready` and `/stats` are the real oracles — korbead *computes* them, so agreement is evidence the language executed the logic correctly. `/issues/{id}` is a round-trip check: korbead decodes and re-encodes that JSON, so agreement proves decode/encode fidelity rather than logic. Both are worth having; do not overclaim the second.

**Drift is the trap here, and it is not hypothetical.** korbead serves a *frozen* snapshot; `bd` is *live*. This project files beads as it goes, so `bd` moves under the oracle constantly — Task 3's reviewer already observed the two diverging mid-session. An oracle that compares live `bd` against a stale snapshot reports a korbead defect that does not exist.

So the harness separates the two questions rather than conflating them:

1. **Is korbead computing correctly?** Compare korbead's endpoints against a computation over `data/issues.json` — the exact bytes the running service loaded. This is the real correctness check and it cannot drift.
2. **Is the snapshot fresh?** Separately, compare `data/issues.json` against live `bd list --all --json`. A mismatch here means "re-run `./bin/snapshot.sh` and restart the service", not "korbead is wrong".

Report the two independently. Never let a stale snapshot be reported as a logic failure.

bad = [k for k, v in expected.items() if got.get(k) != v]

bad = []

if bad:
    print(f"  MISMATCH on {len(bad)} issues: {bad[:5]}")
    print("  A mismatch here means Korben's JSON encode/decode is lossy — file it as a Korben bug.")
    sys.exit(1)

PYEOF

"""Grow the snapshot to N issues by cloning real ones with fresh ids.

The shape has to stay real — same fields, same dependency records — or the
measurement is about a fiction rather than about korbead.
"""
import json, sys, copy
target = int(sys.argv[1]) if len(sys.argv) > 1 else 5000
base = json.load(open("data/issues.json"))
out, i = list(base), 0
while len(out) < target:
    src = copy.deepcopy(base[i % len(base)])
    src["id"] = f"synth-{i}"
    src["title"] = f"{src.get('title','')} (synthetic {i})"

    # than anything else in this file: with EMPTY dependencies, `ready` never
    # performs a lookup and scales LINEARLY, which would produce a confident
    # false refutation of H1. Measured: empty deps give 1ms -> 3ms from 250 to
    # 2000 issues; dependency-bearing deps give 18ms -> 1518ms over the same
    # range. A real tracker has dependency chains; model them.
    src["status"] = "open"
    src["dependencies"] = ([{"depends_on_id": f"synth-{i-1}", "type": "blocks"}]
                           if i > 0 else [])
    out.append(src); i += 1
json.dump(out, open("data/issues-large.json", "w"))
print(f"wrote data/issues-large.json ({len(out)} issues)")

- [ ] **Step 4a: Measure H1 directly, at the function level — do this FIRST**

Before any HTTP is involved, measure `issues.ready` itself. This isolates the language cost from the server entirely and is the cleanest evidence the project can produce. **I have already run this; your job is to reproduce it and extend it.** Preliminary results, native release build:

| issues | `ready` | ratio | linear filter |
|---:|---:|---:|---:|
| 250 | 18 ms | — | 1 ms |
| 500 | 89 ms | 4.9× | 0 ms |
| 1000 | 372 ms | 4.2× | 0 ms |
| 2000 | 1518 ms | 4.1× | 2 ms |

Doubling the corpus quadruples the time — O(n²) — while an equivalent linear filter over the same data stays at 0-2ms.

Build a small timing harness that loads a corpus, times `issues.ready`, times `issues.by-status` as a linear control, and prints both:

```korben
(module main
  (use issues :as issues)
  (use std.process :as process)
  (use std.time :as time))

(pub fn main [] -> Unit !io
  (let path (match (process.args) [p] p _ "data/issues.json"))
  (match (issues.load path)
    (Err m) (println "load failed:" m)
    (Ok all)
      (do
        (let t0 (time.now-millis))
        (let r (len (issues.ready all)))
        (let t1 (time.now-millis))
        (let f (len (issues.by-status all "open")))
        (let t2 (time.now-millis))
        (println (format "n={(len all)} ready={r} ready_ms={(- t1 t0)} filter_ms={(- t2 t1)}")))))
```

Run it against corpora of 250, 500, 1000, 2000 and 5000 in a `--release` build. Record the ratios.

**The measurement trap — read this before generating corpora.** The quadratic only appears with *dependency-bearing* data. A corpus with empty `dependencies` shows `ready` scaling linearly (1ms → 3ms from 250 to 2000), because `dependency-satisfied?` never performs a lookup. The synthesizer in Step 1 generates blocking dependencies for exactly this reason. If your numbers come out linear, check the corpus before concluding anything.

- [ ] **Step 4b: Measure H1's sharpest case — `/ready` at scale**

`issues.ready` resolves each issue's blocking dependencies with `issues.find`, a linear scan, giving O(N²·D). The usual remedy — build an id→issue index once and look up in O(1) — **is not expressible in korben**: `Map` is a linear scan (`value.rs:46-52`), `Set` is an `Rc<Vec<Value>>` (`value.rs:28`), and no hash-based structure exists in the runtime at all. Verified.

This is not a confound to design around. It IS the measurement: `/ready` is the endpoint where korben's lack of a sub-linear lookup has nowhere to hide.

```bash
./bin/synthesize.py 1000
KORBEAD_ISSUES=data/issues-large.json korben run -- serve & sleep 2
oha -z 15s -c 8 --no-tui http://127.0.0.1:3000/ready | grep -E "Requests/sec|Average"
kill %1
./bin/synthesize.py 5000
KORBEAD_ISSUES=data/issues-large.json korben run -- serve & sleep 2
oha -z 15s -c 8 --no-tui http://127.0.0.1:3000/ready | grep -E "Requests/sec|Average"
kill %1
```

**The control is `/issues?status=open`, NOT `/stats`.** This matters and it is easy to get wrong — I did, in an earlier draft of this plan. `stats` calls `ready` *twice* (`src/issues.kb:89-90`, once for `:blocked` and once for `:ready`), so `/stats` is strictly *more* quadratic than `/ready`. Comparing the two would produce two similar curves and a false conclusion that the quadratic does not matter.

`/issues?status=open` filters linearly and performs no per-issue `find`, so it is a genuine control. Run it at the same corpus sizes:

```bash
oha -z 15s -c 8 --no-tui "http://127.0.0.1:3000/issues?status=open" | grep -E "Requests/sec|Average"
```

Record the scaling curve for `/ready` and `/issues?status=open` at 1000 and 5000. A 5× corpus growth producing far worse than 5× latency on `/ready` while `/issues` stays near-linear confirms H1 in the strongest available form and directly justifies bead `korben-90o`.

**Also measure `/stats` and report it separately as a finding in its own right.** It should be roughly twice `/ready`'s cost. That is worth stating plainly: the most innocuous-looking endpoint in the service — a counts summary — is the single most expensive one, because a quadratic helper got called twice inside a map literal where nothing makes the cost visible. That is what the absence of a sub-linear lookup does to ordinary code written without thinking about it.
