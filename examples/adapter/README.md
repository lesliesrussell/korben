# A Rust library, called from Korben

One directory, two halves of the same library.

- `src/lib.rs` is ordinary Rust. `#[korben_export]` adds an `extern "C"` shim
  beside each annotated function; the functions themselves are unchanged, and
  ordinary Rust callers keep using them. Its tests prove that.
- `src/slug.kb` is generated by `korben ffi rust` from the same signatures. It
  has two layers: the `raw-` declarations are the foreign contract, and each is
  unsafe; the wrappers over them are what Korben code imports.
- `src/main.kb` uses the wrappers.

Both halves are rendered from one reading of the signature, so they cannot
disagree about a type, a symbol name, or what may cross.

## Running it

```sh
cargo build                                       # the Rust half
korben ffi rust src/lib.rs --library slug \
  --module slug --out src/slug.kb                 # the Korben half

DYLD_LIBRARY_PATH=target/debug korben run         # macOS
LD_LIBRARY_PATH=target/debug korben run           # Linux
```

`korben build` produces a native executable that calls the same library the
same way; `crates/korben-cli/tests/native.rs` runs both and requires the output
to match byte for byte.

The loader needs to find `libslug`, which is why the library path is set above.
Naming a file directly works too — `--library ./target/debug/libslug.dylib` —
since a library name containing a `/` or a `.` is used as a path.

## What crosses

`i64`, `f64`, `bool`, `&str`, and `String`, plus `Result<T, E>` for any
printable `E`. A signature outside that is declined by name rather than guessed
at: a foreign signature must be all-integer or all-floating, so a function
mixing `&str` and `f64` parameters has no calling convention to use.

Every wrapper returns a `Result` even where the Rust function does not, because
the boundary can fail where the function cannot: the adapter may have panicked,
and a returned string may be one C cannot carry. `truncate` in `main.kb` shows a
Rust `Err` arriving as a Korben `Err`.
